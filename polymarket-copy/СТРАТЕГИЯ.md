# Стратегия отбора кошельков Polymarket для копирования фиксированной суммой

## 1. Главный принцип

При копировании фиксированной суммой результат копировщика равен
`фикс × Σ доходность_сделки`. Поэтому кошельки отбираются не по долларовому
PnL и не по винрейту, а по **равновзвешенной доходности на сделку**,
пересчитанной так, как будто каждую сделку взял копировщик: с задержкой,
с проскальзыванием на свою сумму и с комиссией.

Долларовый PnL обманывает дважды: он взвешен размером ставок кошелька
(один крупный выигрыш перекрывает сотню мелких проигрышей) и он не
различает «купил по 0,95 и выиграл» от «купил по 0,40 и выиграл».
Пример из реального прогона: кошелёк с +229 000 $ долларового PnL имеет
равновзвешенную доходность −73 % на позицию. Копируя его фикс суммой,
вы теряли бы три четверти каждой ставки.

## 2. Данные

| Что | Откуда |
|---|---|
| Сделки кошелька, до 10 500 последних | `data-api.polymarket.com/trades?user=` |
| Все позиции кошелька, включая проигранные | `data-api.polymarket.com/positions?user=` |
| Выкупленные выигрыши | `data-api.polymarket.com/closed-positions?user=` |
| Глобальная лента сделок, до 10 000 последних | `data-api.polymarket.com/trades` |
| Рынок: резолв, объём, тип, серия, время матча | `gamma-api.polymarket.com/markets?condition_ids=` |
| Теги события | `gamma-api.polymarket.com/events/{id}` |
| История цены токена по минутам | `clob.polymarket.com/prices-history` |
| Стакан | `clob.polymarket.com/book` |

Две ловушки API, найденные при реализации:

- `closed-positions` содержит только **выкупленные выигрыши**. Проигранные
  позиции лежат в `positions` с ценой 0. Считать винрейт по одному
  `closed-positions` нельзя, он всегда будет 100 %.
- `markets?condition_ids=` по умолчанию отдаёт только открытые рынки.
  Резолвнутые надо запрашивать отдельно с `closed=true`.

## 3. Пересчёт под фикс сумму

История сделок кошелька собирается в **эпизоды**: от первой покупки токена
при нулевом остатке до полной продажи либо резолва рынка. На эпизод
считаются три доходности, все на одну ставку:

- `r_copy`: вход по цене **первой** покупки эпизода, выход пропорционально
  продажам кошелька, остаток по резолву. Это то, что получит копировщик.
- `r_hold`: тот же вход, но держим до резолва, продажи кошелька игнорируем.
  Сравнение `r_copy − r_hold` показывает, добавляют ли его выходы ценность.
- `r_wallet`: фактическая доходность кошелька на вложенный доллар.

Реалистичный вход считается отдельно на стадии 3 и в симуляции: бот ставит
рыночный ордер через 30 секунд после его сделки, значит покупка идёт по
**аску**, продажа по **биду**. Истории стакана API не отдаёт, но лента сделок
рынка тейкерская: покупка тейкера показывает аск, продажа тейкера показывает
бид, сделки по противоположному токену пересчитываются как 1 − p
(`pm/quotes.py`). Если аск в окне не наблюдался, берётся бид плюс типичный
спред этой ленты. Если edge исчезает уже при 30 секундах, кошелёк живёт
скоростью и не копируется.

## 4. Воронка

### Стадия 0. Сбор кандидатов

Лидерборд не годится: он по долларам, там киты и маркетмейкеры. Кандидаты
собираются из глобальной ленты сделок на нескольких порогах минимальной
суммы сделки и из сделок по самым оборотистым рынкам суток. За один день
это 20 000+ адресов.

### Стадия 1. Дешёвые отсечки, 2–25 запросов на кошелёк

Объединяются `positions` и `closed-positions` в одном временном окне.

| Критерий | Порог | Зачем |
|---|---|---|
| Резолвнутых позиций | ≥ 50 | статистика |
| Возраст истории | ≥ 90 дней | пережил хотя бы один сезон |
| Позиций за жизнь | ≤ 5000 | больше это бот |
| Открытых позиций сейчас | ≤ 10 | бюджет |
| Равновзвешенный ROI | > 0 | суть метода |
| Доля входов ≥ 0,90 | ≤ 50 % | «винрейт 93 % по 0,95» |
| Доля прибыли от входов < 0,10 | ≤ 30 % | лотерея |
| Доля прибыли от лучшей позиции | ≤ 25 % | один счастливый билет |
| Доля 5-минутных крипторынков | ≤ 50 % | шум и латентность |

Реальный прогон одного дня: из 19 153 кошельков эту стадию проходят
единицы процентов. Главные причины отсева: мало истории, ROI ≤ 0,
концентрация прибыли.

### Стадия 2. Полная история сделок

| Критерий | Порог |
|---|---|
| 95-й перцентиль одновременно открытых позиций | ≤ 8 |
| Медианный объём рынка | ≥ 30 000 $ |
| Медиана удержания | ≥ 1 час |
| Доля рынков, где держал обе стороны | ≤ 10 % |
| Входы ≥ 0,95 за 10 минут до конца рынка | ≤ 10 % |
| t-статистика среднего `r_copy` | ≥ 2 |
| Просадка в ставках | ≤ 10 |
| Обе половины истории в плюсе | да |

Дополнительно считаются, но не отсекают: edge по ценовым корзинам
(винрейт минус цена входа), доля живых ставок во время матча, сигнал
размера (крупные сделки кошелька лучше мелких?), ценность выходов.

Скор = усечённое среднее `r_copy` × min(1, t/3) × штраф за нестабильность.

### Сегментация

Дерево: категория → вид спорта или тема → лига или серия → тип рынка →
ценовая корзина → живой рынок или предматч. Сегмент **утверждается** только
если одновременно:

- n ≥ 30 резолвнутых эпизодов;
- t ≥ 2;
- среднее со сжатием к общему среднему кошелька положительно:
  `(n × mean_seg + 20 × mean_wallet) / (n + 20) > 0`;
- обе половины истории сегмента в плюсе (walk-forward).

Сжатие обязательно: у кошелька с 30 сегментами один всегда «отличный»
случайно. Кошелёк с отрицательным общим ROI, но утверждённым сегментом
помечается `pass = segment` и копируется только внутри сегмента.

### Стадия 3. Реалистичный вход

По 150 последним эпизодам через историю цен:

- ROI с задержкой 5 и 30 минут, с проскальзыванием 1 %;
- доля сделок, которые копировщик пропустил бы по правилам входа
  (цена ушла больше чем на 3 цента или уже ≥ 0,90);
- маркаут через 1 час и 24 часа: куда идёт цена после его входа;
- проскальзывание фикс суммы по текущим стаканам его открытых рынков.

Проходит, если ROI с задержкой 5 минут > 0 и не хуже 60 % сырого, и
проскальзывание ≤ 1,5 %. Итоговый скор = скор стадии 2 × коэффициент
сохранения edge при задержке.

## 5. Исполнение

- Рыночный ордер через 30 с: покупка по аску, продажа по биду. Не входить,
  если аск выше его цены входа больше чем на 3 цента, или если аск ≥ 0,90.
- Перед входом проверять стакан: глубины на фикс сумму нет в пределах 1,5 %,
  значит пропуск.
- Одна позиция на рынок на портфель. В мультиисходных событиях лимит по
  событию.
- Копировать выходы только если `exit_value_add > 0` у этого кошелька,
  иначе держать до резолва.
- Если `size_signal` заметно положителен, копировать только сделки кошелька
  не ниже его медианного размера.
- Сделки вне утверждённых сегментов кошелька не копировать.

## 6. Портфель и мониторинг

- 5–15 кошельков, не более 3 в одной категории, общий лимит открытых
  позиций на портфель.
- Пересчёт скоринга еженедельно. Выбывание: `roi_last30` < 0, рост доли
  входов ≥ 0,90, рост одновременных позиций, молчание больше 30 дней.
- Кошельки с общим источником финансирования или синхронными сделками
  считать одним.

## 7. Что улучшить дальше

1. **Бэктест воронки целиком**: отобрать по данным до даты T, посмотреть
   результат после T. Единственный честный тест порогов из таблиц выше.
2. **Взвешивание по давности** с полураспадом около 90 дней: свежий edge
   ценнее старого.
3. **Кластеризация адресов** по источнику пополнения и синхронности сделок.
4. **Инсайдерские кошельки** в отдельную корзину с малым весом: молодой
   адрес, мало сделок, огромный edge на политике или событиях.
5. **Комиссии**: Polymarket вводит тейкер-комиссии на части рынков, поле
   `FEE_BPS_BY_CATEGORY` в конфиге под это заведено.
6. **Живой поток**: подписка на сделки утверждённых кошельков через
   WebSocket CLOB и автоматическое исполнение по правилам раздела 5.

## 8. Цикл отбора и бумажной проверки (с 22.09.2026)

1. **Батч 1** запущен 22.09.2026 06:37 UTC: 31 кошелёк, прошедший все три стадии,
   пять из них помечены `top5`. Копия $1 на каждую новую позицию, старт $100.
2. Раз в два дня: сбор кошельков дня, воронка, запись в реестр, обновление симуляции.
3. Через неделю: `sim.py review --batch 1`, кошельки с положительным PnL и не менее
   5 закрытых позиций уходят в `positive.json`, остальные помечаются `negative`.
   Разбор: какие критерии стадий 1–3 не отличили плюс от минуса, правка порогов.
4. Следующий батч: свежие прошедшие стадию 3, ещё не бывшие в симуляции.

Ожидания по объёму: у отобранных кошельков 1–3 новые позиции в день, за неделю это
5–20 сделок на кошелёк. На таком объёме шум велик, поэтому решение по батчу лучше
принимать по сумме батча и по PnL в утверждённых сегментах, а отдельный кошелёк
переводить в `positive` только при 10+ закрытых позициях; при меньшем числе держать в
симуляции ещё неделю.
